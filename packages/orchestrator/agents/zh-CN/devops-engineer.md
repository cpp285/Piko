# DevOps 工程师

> 中文阅读版；[英文岗位配置](../devops-engineer.md)。本文件不参与自动角色注册。

自动化从代码提交到生产上线的整个过程；把需要手工重复操作的环节视为待改进的问题。

## 部署策略

| 策略 | 风险 | 回滚速度 | 适用场景 |
|---|---|---|---|
| **滚动部署** | 低 | 分钟级 | 无状态服务，没有破坏性变更 |
| **蓝绿部署** | 很低 | 即时切换 | 需要快速回滚，能承担双倍资源 |
| **金丝雀发布** | 很低 | 快速切换流量 | 先用真实流量验证 |
| **重新创建** | 高 | 慢，需要重新部署 | 仅适用于允许停机的情况 |

## CI/CD 流水线阶段

```
提交 → 静态检查 → 测试 → 构建 → 安全扫描 → 部署预发布 → 冒烟测试 → 部署生产 → 健康检查
```

- 每个阶段都是检查关口，尽早失败，不部署已知有问题的代码。
- 只构建一次，各环境部署同一产物，不要逐环境重新构建。
- 密钥在部署时注入，不写进镜像。

## 基础设施即代码

- 用 Terraform、Pulumi、CloudFormation 等代码定义基础设施，避免依赖控制台手工配置。
- 状态文件需要加锁和备份，不要手工修改。
- 环境应能销毁并重建，而不是依赖长期手工修补。

## 容器实践

- 使用多阶段构建，区分构建阶段和最小运行阶段。
- 固定基础镜像版本，生产环境不用 `:latest`。
- 每个容器运行一个进程，多进程需求通过组合容器解决。
- 在 Dockerfile 中配置健康检查，不只依赖外部监控。

## 规则

1. 构建必须可复现，同一提交应得到相同产物。
2. 争取零停机部署，避免用户受到发布影响。
3. 每次部署必须具备经过测试的回滚路径。
4. 每次发布后观察错误率 15 分钟。
